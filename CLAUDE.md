## Project Overview

## Техническое задание на разработку бота для тайм-трекинга сотрудников (дополняемое)
**Платформа:** Яндекс Мессенджер (корпоративный)  
**Среда исполнения:** Linux, Python 3.11+, PostgreSQL 15+, systemd  
**Режим развёртывания:** неконтейнеризованный (на «голой» ОС)  
**Ключевые особенности:** многопользовательская работа, изоляция состояний через БД, шифрование каналов связи и данных  

---

### 1. Общие сведения
**Наименование системы:** Яндекс-мессенджер-бот учёта рабочего времени сотрудников.
**Цель:** Автоматизация фиксации начала/окончания работы, перерывов, с привязкой к задачам, с хранением истории в защищённой БД.
**Среда выполнения:** Сервер под управлением Linux (systemd), Python 3.11+, PostgreSQL 15+.
**Особые требования:**
- Все соединения с БД должны быть зашифрованы (TLS/SSL).
- Конфиденциальные данные в базе (названия задач и имена пользователей) должны храниться в зашифрованном виде.
- Управление процессом бота через systemd unit.
- Взаимодействие с Яндекс мессенджер API происходит по HTTPS (уже зашифровано).
- Работа с напоминаниями пользователей
**Пользователи:** Сотрудники организации, авторизованные в Яндекс Мессенджере (идентификация по корпоративному логину/email).
**Модель взаимодействия:** Асинхронный Webhook-сервер, получающий события от Bot API Яндекс Мессенджера, и отправляющий ответные сообщения через REST API.
---

### 2. Функциональные требования

#### 2.1. Пользовательские состояния (FSM)
Бот должен реализовывать конечный автомат со следующими состояниями:
- **Idle** – состояние по умолчанию.
- **Working** – активная работа над задачей.
- **OnBreak** – перерыв \ обед (приостановка текущей задачи).

#### 2.2. Клавиатуры и команды
В зависимости от состояния пользователю показываются клавиатуры с кнопками:
- **Idle:** `\[Начать работу]`
- **Working:** `\[Закончить]`, `\[Перерыв]`, `\[Сменить задачу]`
- **OnBreak:** `\[Вернуться]`

Также бот должен обрабатывать команду `/start`, которая сбрасывает состояние на `Idle`.

#### 2.3. Бизнес-логика обработки действий

| Действие | Текущее состояние | Результат |
|----------|-------------------|-----------|
| Нажатие «Начать работу», вопрос от бота, Ввод названия задачи  | Idle | Создаётся новая рабочая сессия (начало), задача запоминается, статус меняется на Working. |
| Нажатие «Закончить» | Working | Текущая рабочая сессия закрывается (end_time), статус Idle. |
| Нажатие «Перерыв» | Working | Начинается перерыв (создаётся сессия с task_name='Break'), статус OnBreak. |
| Нажатие «Сменить задачу» | Working | Текущая сессия для текущей задачи завершается, начинается новая сессия для новой задачи, статус не меняется -  Working. |
| Нажатие «Вернуться» | OnBreak | Перерыв завершается, статус возвращается в Working, возобновляется предыдущая задача. |
| `/start` | Любое | Сброс в Idle. |
| `/new\_rem` | Любое | Состояние не меняется. Ожидание ввода текста и времени напоминания, распознавание времени и текста напоминания, запись в бд напоминания, сообщение пользователю «Напоминание <текст сохраненного напоминания> сработает <когда сработает напоминание>» |
| `/list\_rem` | Любое | Состояние не меняется. Запрос из бд и вывод пользователю список его напоминаний `is\\\_done`==False |

Все переходы между состояниями должны фиксироваться в БД: записываются сессии работы (с названием задачи) и сессии перерывов с временными метками.

#### 2.4. Многопользовательская работа
- Бот обслуживает неограниченное число сотрудников одновременно.
- Состояния разных пользователей изолированы: каждый сотрудник взаимодействует со своей независимой сессией (данные хранятся в БД, ключ – user_login).
- Асинхронный веб-сервер должен обрабатывать входящие сообщения конкурентно, без взаимных блокировок.

---

### 3. Интеграция с Яндекс Мессенджером

#### 3.1. Получение событий (Webhook)
- После запуска бот должен зарегистрировать Webhook URL в Bot API или получить его через ручную настройку в панели управления (требуется публичный HTTPS-адрес).
- Формат входящего сообщения – JSON. Из него необходимо извлечь:
  - `user_login` (строка, идентификатор пользователя в организации)
  - `chat_id` (идентификатор чата, для отправки ответа)
  - `text` (текст сообщения или нажатая кнопка)
- При старте бот проверяет доступность API, устанавливает Webhook.

#### 3.2. Отправка сообщений
- Для отправки используется Bot REST API Яндекс Мессенджера (метод `sendMessage`).
- Сообщение должно содержать:
  - `chat_id`
  - `text`
  - `keyboard` – объект с массивом кнопок (при необходимости)
- Аутентификация осуществляется OAuth-токеном, передаваемым в заголовке `Authorization`.

#### 3.3. Особенности платформы
- Идентификатор пользователя – `user_login` (обычно email), имеет строковый тип.
- Команда `/start` доступна как обычное сообщение (может быть отправлена системой при первом открытии чата).
- Не поддерживаются inline-кнопки, только reply-клавиатуры.

### 4. Схема базы данных

Используется PostgreSQL. Для шифрования данных применяется модуль `pgcrypto` и/или шифрование на стороне приложения (Fernet).
#### 4.1. Таблицы:

1. **users** – сотрудники
   - `id` SERIAL PRIMARY KEY
   - `name` VARCHAR(255) NOT NULL
   - `yandex\_user\_login` BIGINT UNIQUE NOT NULL – логин в Яндекс Мессенджере
   - `scheduled\_work\_start` TIME
   - `scheduled\_work\_end` TIME

2. **current_status** – текущее состояние пользователя
   - `user\_id` INTEGER PRIMARY KEY REFERENCES users(id)
   - `current\_state` VARCHAR(50) NOT NULL DEFAULT 'idle'
   - `current\_task\_id` INTEGER REFERENCES user_tasks(id)

3. **user_tasks** – история задач для быстрого выбора
   - `id` SERIAL PRIMARY KEY
   - `user\_id` INTEGER REFERENCES users(id)
   - `task\_name\_encrypted` BYTEA или TEXT – хранит зашифрованное название задачи (шифрование на стороне бота).
     *Для поиска дубликатов может дополнительно храниться хеш (HMAC) названия.*

4. **sessions** – журнал рабочих и перерывных сессий
   - `id` SERIAL PRIMARY KEY
   - `user\_id` INTEGER REFERENCES users(id)
   - `task\_name\_encrypted` TEXT – зашифрованное название задачи или 'Break' (не шифруется)
   - `start\_time` TIMESTAMP DEFAULT NOW()
   - `end\_time` TIMESTAMP

5. **reminders** – напоминания (опционально)
   - `id` SERIAL PRIMARY KEY
   - `user\_id` INTEGER REFERENCES users(id)
   - `text` TEXT
   - `scheduled\_time` TIMESTAMP
   - `is\_done` BOOLEAN DEFAULT FALSE  

#### 4.2. Шифрование данных
- Названия задач шифруются перед сохранением симметричным алгоритмом (Fernet).  
- Ключ шифрования загружается из переменной окружения `ENCRYPTION_KEY`.  
- Для поиска задачи по названию можно дополнительно хранить HMAC‑хеш (ключ для HMAC отдельный) или выполнять поиск с расшифровкой (при небольшом количестве задач это допустимо).  
- Текст «Break» не шифруется.

### 5. Требования к безопасности

#### 5.1. Защита каналов связи
- **Подключение к Bot API:** обязательно использование HTTPS (платформа сама требует валидный SSL‑сертификат для Webhook).  
- **Подключение к PostgreSQL:** только SSL‑соединения (`hostssl` в `pg_hba.conf`). Сервер БД должен иметь сертификат, клиент проверяет его (режим `verify‑ca` или `verify‑full`).  

#### 5.2. Хранение секретов
- Токен бота (`YANDEX_OAUTH_TOKEN`), строка подключения к БД, ключ шифрования хранятся в файле `/etc/timetracker-bot/env` с правами `640` и владельцем `root:timetracker_bot`.  
- В коде секреты не зашиваются.

#### 5.3. Системная безопасность
- Бот работает от непривилегированной учётной записи `timetracker_bot`.  
- В systemd-юните применены директивы: `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `ReadWritePaths=/opt/timetracker-bot /var/log`.

### 6. Архитектура приложения

**Язык:** Python 3.11+  
**Веб-фреймворк:** aiohttp (рекомендуется) или FastAPI для приёма Webhook-запросов.  
**ORM:** SQLAlchemy 2.0 (асинхронный режим) + asyncpg.  
**Шифрование:** библиотека `cryptography` (Fernet + HMAC).  
**HTTP-клиент для Bot API:** `aiohttp` (прямые запросы) или специализированная библиотека (например, `yambot-client`).  

**Структура проекта** (размещается в `/opt/timetracker-bot/`):
```
├── main.py              # запуск приложения, настройка маршрутов
├── bot_api.py           # функции отправки сообщений и работы с клавиатурами
├── db.py                # модели, engine, функции работы с БД, шифрование
├── fsm.py               # реализация конечного автомата (контроль переходов)
├── handlers.py          # обработчики входящих сообщений
├── config.py            # загрузка переменных окружения
├── requirements.txt
```

#### 6.1. Обработка сообщений (handlers)
Для каждого входящего сообщения:
1. Извлекается `user_login` и `chat_id`.
2. Открывается асинхронная сессия БД.
3. Определяется текущее состояние пользователя (из `current_status`).
4. Вызывается соответствующий обработчик, реализующий бизнес-логику.
5. При необходимости изменяется состояние, фиксируются записи в БД.
6. Формируется ответное сообщение с обновлённой клавиатурой.

#### 6.2. Реализация FSM (без aiogram)
Состояния и их переходы определяются словарём или классом. Основная функция `process_message` выбирает ветку логики в зависимости от `current_state` и содержимого сообщения (кнопка/текст).  
Примерная схема:
```python
async def process_message(user, state, text, ...):
    if state == IDLE and text == "Начать работу":
        await set_state(user, ENTERING_TASK)
        await send_message(chat_id, "Введите название задачи:", keyboard=None)
    elif state == ENTERING_TASK:
        # text - название задачи
        await start_work_session(user, text)
        await set_state(user, WORKING, task_id=...)
        await send_message(chat_id, f"Задача «{text}» начата.", keyboard=WORKING_KB)
    # ... остальные состояния
```

#### 6.3. Многопользовательская конкурентная обработка
- Используйте `aiohttp.web` с асинхронными handler’ами. Каждый запрос обрабатывается в отдельной корутине.
- Состояния пользователей изолированы, поскольку ключом является `user_login`, а не глобальная переменная.
- При использовании `asyncpg` и `SQLAlchemy` пул соединений должен быть достаточным для параллельной работы (настраивается при создании `AsyncEngine`).

### 7. Требования к реализации

1. **Использовать Python ≥ 3.11**, асинхронный стек: `aiohttp` + `aiosignal` (или `FastAPI` + `uvicorn`).
2. **База данных:** все операции выполняются через `asyncpg` и `SQLAlchemy 2.0`. Миграции создаются при старте (`Base.metadata.create_all`) или через Alembic (опционально).
3. **Шифрование:**
   - Функции `encrypt_value(plain: str) -> str` и `decrypt_value(cipher: str) -> str` используют `Fernet`.
   - При сохранении задачи вызывается `encrypt_value`.
   - При отображении пользователю – `decrypt_value`.
4. **Логирование:** весь вывод направляется в stdout (для `journalctl`). Уровень логирования настраивается через переменную окружения.
5. **Обработка ошибок:**
   - Недоступность Bot API – повтор с экспоненциальной задержкой.
   - Сбой соединения с БД – повтор транзакции до 3 раз, затем возврат сообщения об ошибке пользователю.
6. **Запуск:** приложение должно запускаться из `main.py` командой `python main.py`, не требуя дополнительных аргументов. Порт для Webhook берётся из переменной `LISTEN_PORT` (по умолчанию 8443).
7. **Первый вход пользователя:** если после команды /start оказывается, что пользователя нет в таблице users, то происходит его регистрация: указывается какую информацию можно писать в бота и спрашивается имя пользователя. Пользователь вносится в таблицу users в бд.

### 8. Развёртывание и запуск

1. **Системные зависимости:**
   ```bash
   sudo apt install postgresql python3.11-venv
   ```
2. **Создание пользователя:**
   ```bash
   sudo useradd -r -s /bin/false timetracker_bot
   ```
3. **Размещение кода:** клонировать репозиторий в `/opt/timetracker-bot`, установить виртуальное окружение и зависимости.
4. **PostgreSQL:**  
   - Включить SSL, создать сертификаты.  
   - Создать БД `timetracker` и пользователя `timetracker_bot` с паролем.  
   - В `pg_hba.conf` разрешить `hostssl` для этого пользователя.
5. **Конфигурация бота:** создать `/etc/timetracker-bot/env`:
   ```ini
   YANDEX_OAUTH_TOKEN=<токен>
   DATABASE_URL=postgresql+asyncpg://timetracker_bot:pass@localhost:5432/timetracker
   ENCRYPTION_KEY=<base64-encoded-32-byte-key>
   LISTEN_PORT=8443
   WEBHOOK_URL=https://your-public-domain.com/webhook
   ```
6. **Systemd unit** `/etc/systemd/system/timetracker-bot.service`:
   ```ini
   [Unit]
   Description=Time Tracker Bot (Yandex Messenger)
   After=network-online.target postgresql.service
   Wants=network-online.target

   [Service]
   Type=simple
   User=timetracker_bot
   Group=timetracker_bot
   WorkingDirectory=/opt/timetracker-bot
   EnvironmentFile=/etc/timetracker-bot/env
   ExecStart=/opt/timetracker-bot/venv/bin/python main.py
   Restart=always
   RestartSec=10
   NoNewPrivileges=yes
   PrivateTmp=yes
   ProtectSystem=strict
   ProtectHome=yes
   ReadWritePaths=/opt/timetracker-bot /var/log

   [Install]
   WantedBy=multi-user.target
   ```
7. **SSL-сертификат для Webhook:** настроить reverse-прокси (nginx) с Let’s Encrypt, который будет проксировать запросы на `localhost:8443`, или использовать встроенный в Python TLS (тогда потребуется указать пути к сертификатам в переменных окружения).

### 9. Тестирование

- Проверить все переходы состояний для одного пользователя.
- Проверить одновременную работу 3–5 пользователей: состояния не должны пересекаться.
- Убедиться, что названия задач в БД зашифрованы (кроме “Break”).
- Проверить SSL-подключение к PostgreSQL (логи `postgresql` должны содержать `SSL connection`).
- Убедиться, что при перезапуске бота состояние пользователя восстанавливается из `current_status`.
- Проверить отказоустойчивость: остановка БД, потеря сети – бот должен корректно обрабатывать ошибки и продолжать работу после восстановления.
